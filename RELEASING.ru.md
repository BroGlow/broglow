# Выпуск и публикация

Это инструкция для сопровождающих, работающих с исходниками. Упомянутые ниже
файлы `site/` и `.github/` не входят в готовые пакеты приложения.

Выпуск приложения/прошивки и публикация сайта используют отдельные процессы
GitHub Actions. Файлы STL и STEP распространяются только внутри ZIP-архива
корпуса, приложенного к релизу; все сгенерированные файлы оставляйте
игнорируемыми и вне Git (см. [CONTRIBUTING.ru.md](CONTRIBUTING.ru.md)).

<a name="distribution"></a>

## Распространение

| Загрузка | Содержимое |
| --- | --- |
| `broglow-vVERSION-aarch64-apple-darwin.tar.gz` | Приложение для Apple Silicon, прошивка C3 и её исходники, руководство, лицензии и контрольные суммы. |
| `broglow-vVERSION-x86_64-apple-darwin.tar.gz` | Такой же пакет с нативным приложением для Mac на Intel. |
| `broglow-vVERSION-x86_64-pc-windows-msvc.tar.gz` | Графическое приложение в трее и CLI для Windows в `broglow.exe`, с поддержкой лампы по USB, лицензией и уведомлениями о сторонних компонентах; без установщика, BLE, прошивки и руководств. |
| `broglow-models-vVERSION.zip` | Файлы корпуса для печати: пять рабочих деталей 01–05 в `stl/` (ориентация печати) и `step/`, а также `BUILD.json`. Маскот держится на четырёх магнитах Ø3×2 мм N52 (два в маскоте, два в светофоре). |
| Соответствующий `.sha256` | Контрольная сумма каждого архива с его исходным именем. |

Пакеты Mac также содержат `BUILD.json`, внутренний `SHA256SUMS`, адреса записи
прошивки и минимальную версию macOS, извлечённую из исполняемого файла.
Приложение устанавливается по приложенному [руководству](site/guide/ru/hardware.md#install-a-prebuilt-package).
Каждый архив приложения содержит `THIRD-PARTY-NOTICES.md` для Rust-крейтов в
исполняемом файле этой платформы и уведомления стандартной библиотеки Rust; пакеты
для Mac добавляют скомпонованные библиотеки прошивки. Их создаёт
[`scripts/third-party-notices.py`](scripts/third-party-notices.py) из
`Cargo.lock`, исходников крейтов и карты компоновки прошивки; упаковка запускает
его сама. Сборки не подписаны сертификатом Developer ID и не нотаризованы Apple.
На Linux приложение собирают из исходников. Формулу Homebrew публикует в
отдельный репозиторий `broglow/tap` [workflow Homebrew tap](#homebrew-tap);
процесса публикации в crates.io нет.

О предупреждениях безопасности GTK 3 для трея на Linux см. [CONTRIBUTING](CONTRIBUTING.ru.md#development-setup).

<a name="python-version"></a>

## Версия Python

Релизы, CI прошивки и Pages используют **Python 3.14**. Корневые инструменты Python
и прошивки берутся из `pyproject.toml` + `uv.lock`; сборки прошивки используют
**PlatformIO Core 6.2.0** и esptool **5.4.0**.

Проверенные хеши STL получены на **macOS 15 на Apple Silicon с Python 3.14**
(`macos-15` в релизном CI). На других платформах байты STL могут отличаться, и
проверка хешей не пройдёт; принимайте новые хеши только после настоящей нарезки
в слайсере на этой платформе.

<a name="build-a-draft-release"></a>

## Подготовка черновика релиза

Укажите версию в `Cargo.toml` и запустите `cargo check`, чтобы `Cargo.lock`
совпадал. Релизный тег **vVERSION** должен указывать на проверенный релизный коммит.
Проверьте исходники и сайт командами из
[CONTRIBUTING.ru.md](CONTRIBUTING.ru.md#build-and-test) и
[инструкции по сайту](site/README.ru.md#check-changes).

После проверки коммита и места назначения явно создайте тег и отправьте
изменения. Замените `YOUR_REMOTE` именем удалённого репозитория GitHub (`git remote -v`):

```bash
git tag vVERSION
uv run --frozen python scripts/package-macos.py --release-tag vVERSION --check-only
git push YOUR_REMOTE HEAD:master
git push YOUR_REMOTE vVERSION
```

Если проверка не прошла (незакоммиченные изменения или несовпадение версии),
удалите локальный тег командой `git tag -d vVERSION`, исправьте проблему и
повторите. Отправка в `master` запускает CI, а если она меняет сайт,
документацию, модели или `Cargo.toml`, ещё и автоматически публикует сайт.

Отправляйте только этот тег, по имени; никогда не используйте `git push --tags`.
Отправка тега `v*` запускает процесс **Release**. Для
следующего релиза поднимите `version` в `Cargo.toml` и `Cargo.lock`, закоммитьте,
затем создайте и отправьте его тег: `git push YOUR_REMOTE vX.Y.Z`.

Процесс **Release** выполняется в таком порядке:

1. Задание `source` на Apple Silicon `macos-15` запускает тесты упаковки и
   проверяет тег, версию и отсутствие незакоммиченных изменений. Оно
   устанавливает закреплённые CAD-зависимости Python и генерирует корпус из
   тега: пять рабочих деталей с файлами STL и STEP. Точные хеши
   STL сверяются с проверенными результатами проверки в слайсере, и создаётся
   ZIP со своим `.sha256`. Затем задание
    проверяет актуальность экспорта веб-модели
    (`scripts/export-web-model.py --check`), а финальная проверка чистоты
    исходников защищает отслеживаемые файлы от изменений сгенерированными отчётами.
2. Затем запускаются переиспользуемый набор CI и проверки процесса **Website**,
   без развёртывания сайта. CI включает форматирование, lint и тесты Rust,
   форматирование Python и прошивки, интеграцию JavaScript, проверки упаковки и
   сгенерированных файлов, проверки прошивки на компьютере и обе сборки C3.
3. Когда обе проверки пройдены, нативные исполнители Apple Silicon и Intel
   собирают и упаковывают приложение для Mac и прошивку C3, а исполнитель
   Windows собирает приложение в трее и CLI.
4. Последнее задание проверяет каждый ожидаемый архив, его контрольную сумму и
   уведомления о сторонних компонентах, затем создаёт **черновик GitHub
   Release**. К нему прикладываются только архивы и их файлы `.sha256`.

Перед нажатием **Publish release** в GitHub:

- Скачайте подходящий архив Mac и его контрольную сумму из черновика.
  Пройдите приложенное руководство от распаковки до установки; проверьте
  `--version`, сервис при входе в систему, разрешение Bluetooth, сопряжение
  и реальную задачу агента.
- Проверьте `BUILD.json`, содержимое архивов и контрольные суммы. Пакеты
  приложения и ZIP корпуса скачиваются отдельно; исключите референсные
  изображения, файлы восстановления и локальные настройки пользователя
  из всех артефактов.
- Укажите, на каких машинах и какое поведение лампы проверялось фактически.
  Локальная приёмка сейчас охватывает Apple Silicon; успешная сборка Intel
  не является проверкой на оборудовании Intel. Явно укажите непроверенные
  платформы.
- Проверьте сформированные заметки и выберите подходящую отметку релиза
  или предварительного релиза. Публикация черновика делает загрузки
  общедоступными и повторно запускает workflow **Website**, чтобы в руководстве
  появился SHA-256 архива корпуса.

Также проверьте на реальном оборудовании переподключение, все цвета светодиодов
и яркость, гашение устаревшего статуса за десять секунд и посадку в корпусе. Не
перепрошивайте работающую плату только ради проверки процесса выпуска.

<a name="package-locally-without-publishing"></a>

## Локальная упаковка без публикации

[`scripts/package-enclosure.py`](scripts/package-enclosure.py) собирает
релизный пакет корпуса. `--output-dir PATH` выбирает другую
папку; она тоже должна игнорироваться. Для репетиции релиза используйте чистую
рабочую копию с соответствующим тегом и добавьте `--release-tag vVERSION`: этот
строгий режим проверяет тег, версию и чистоту исходников до генерации.

<a name="package-magnetic-enclosure"></a>

### Магнитный корпус

[Руководство по печати магнитного корпуса](site/guide/ru/printing.md) описывает состав печати,
вклейку магнитов и генерацию из исходников. Команда:

```bash
uv run --frozen --only-group cad python scripts/package-enclosure.py
```

Результат — `dist/enclosure/broglow-models-vVERSION.zip` и его
`.sha256`; изолированная генерация выполняется в `dist/enclosure/magnetic-build/source/`.
Экспортируются только рабочие детали 01–05; купонов и нарезанных под принтер
3MF/G-code нет. Исходников CAD и инструкции в архиве нет; инструкция живёт на сайте.

После изменения геометрии в `models/magnetic/refined.py` та же команда намеренно
останавливается с ошибкой **Stale magnetic slicer evidence**: архив собирается
только из STL, совпадающих с проверенной нарезкой. Новые детали остаются в
`dist/enclosure/magnetic-build/source/models/magnetic/` (`stl/`, `step/`,
`validation.json`); нарежьте их и проверьте пробной печатью, прежде чем обновлять
результаты проверки.

Весь каталог `models/broglow/preview/` должен оставаться игнорируемым и
неотслеживаемым, включая рендеры, размерные схемы и задания рендера. Храните в Git
выбранные ресурсы приложения/сайта и проверенные данные валидации.

Разовые отчёты инспекции CAD и задания снимков для отдельных версий не входят
во входные данные сборки; храните их в игнорируемом `dist/enclosure/`, вне Git.
Сборка заново создаёт `validation.json` в изолированном дереве.
Сохраняйте проверенный [`slicer-validation.json`](models/magnetic/slicer-validation.json):
упаковка сверяет его хеши STL, поскольку генерация геометрии не запускает
внешний слайсер повторно.

При несовпадении хеша сначала проверьте закреплённый набор инструментов.
Проверки геометрии не заменяют нарезку, и ни одна из них не подтверждает посадку
напечатанных деталей.

<a name="package-mac-app"></a>

### Пакет приложения для Mac

На Mac соответствующей архитектуры сначала соберите приложение и рабочий
образ C3:

```bash
cargo build --release --locked
uv run --frozen flash --build-only
uv run --frozen python scripts/package-macos.py
```

Получится архив с меткой времени и файл `.sha256` в игнорируемом каталоге `dist/`.
Сам упаковщик ничего не собирает, не устанавливает, не прошивает и не
публикует. Локальные пакеты могут использовать рабочую копию с незакоммиченными
изменениями; `BUILD.json` фиксирует это и хеши входных файлов сборки.
Используйте `--release-tag vVERSION` только для чистой рабочей копии и
соответствующего коммита с тегом; этот режим использует постоянное релизное
имя файла и отказывается перезаписывать существующий архив.

<a name="homebrew-tap"></a>

## Homebrew-tap

`brew install broglow/tap/broglow` устанавливает готовые бинарники релиза для
Mac из отдельного репозитория GitHub `broglow/homebrew-tap`, где лежит только
`Formula/broglow.rb`.

[`scripts/homebrew-formula.py`](scripts/homebrew-formula.py) формирует
формулу из файлов `broglow-vVERSION-*-apple-darwin.tar.gz.sha256` релиза (архивы
для Apple Silicon и Intel в блоках `on_macos`/`on_arm`/`on_intel`, `bin/broglow`,
прошивка и руководства в `share/broglow`, и предупреждение, что `broglow install`
нужно выполнить один раз и после каждого обновления). `tests/test_homebrew_formula.py`
проверяет формирование в CI.

Workflow **Homebrew tap** (`.github/workflows/homebrew-tap.yaml`) запускается
при публикации релиза или вручную: **Actions → Homebrew tap → Run workflow** с
тегом релиза. Он скачивает контрольные суммы из этого релиза, формирует
формулу, кладёт её в локальный tap на macOS-раннере для `brew style` и
`brew audit --strict`, устанавливает и тестирует её и загружает `broglow.rb` как
артефакт `homebrew-formula`. Для опубликованного релиза, а вручную — с отмеченным
**publish**, он затем отправляет `Formula/broglow.rb` в `broglow/homebrew-tap`,
используя секрет репозитория `HOMEBREW_TAP_TOKEN` (fine-grained token с правом
**Contents: read and write** только на `homebrew-tap`). Обновите токен до
истечения его срока.

Для локальной репетиции сформируйте формулу по архивам в `dist/` с
`--url-base file:///путь/к/dist/`, скопируйте её в `brew tap-new broglow/tap`,
выполните `brew style`, `brew audit --strict` и `brew install broglow/tap/broglow`,
затем `brew uninstall broglow` и `brew untap broglow/tap`. Не запускайте
`broglow install` из репетиционного бинарника на машине с рабочей установкой.

<a name="publish-the-website"></a>

## Публикация сайта

Следуйте [инструкции по сайту](site/README.ru.md#publish-to-github-pages), затем
выполните проверку после публикации.

После публикации откройте английское и русское руководства на сайте и
пройдите от ссылки на релиз в Releases этого репозитория до его контрольной
суммы. В руководстве есть отдельная загрузка корпуса, а главная страница
открывается фотографией изделия до загрузки 3D-вида.

Локальные проверки не подтверждают права GitHub, успех облачных исполнителей,
работу опубликованного Pages или установку на другом Mac. Проверяйте это после
каждого релиза и публикации.

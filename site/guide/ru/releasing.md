# Выпуск релизов и публикация сайта

Это инструкция для сопровождающих, работающих с исходниками. Упомянутые ниже
файлы `site/` и `.github/` не входят в готовые пакеты приложения.

Версия релиза: **1.0.0**. Выпуск приложения/прошивки и публикация сайта используют
отдельные процессы GitHub Actions. Распространяйте сгенерированные STL, STEP/STP
и ZIP как файлы релиза; оставляйте их игнорируемыми и вне Git.

<a name="distribution"></a>

## Распространение

| Загрузка | Содержимое |
| --- | --- |
| `broglow-vVERSION-aarch64-apple-darwin.tar.gz` | Приложение для Apple Silicon, прошивка C3 и её исходники, руководство, лицензии и контрольные суммы. |
| `broglow-vVERSION-x86_64-apple-darwin.tar.gz` | Такой же пакет с нативным приложением для Mac на Intel. |
| `broglow-vVERSION-x86_64-pc-windows-msvc.tar.gz` | Графическое приложение в трее и CLI для Windows в `broglow.exe`, с поддержкой лампы по USB и лицензией; без установщика, BLE, прошивки и руководств. |
| `broglow-enclosure-magnetic-vVERSION.zip` | Рекомендуемый съёмный корпус: пять рабочих деталей STL/STEP, виды сборки, исходники, инструкция и отчёты; четыре магнита Ø3×2 мм N52. |
| `broglow-enclosure-vVERSION.zip` | Клеевая альтернатива: STL и STEP, исходники CAD, руководство и отчёты проверок. |
| Соответствующий `.sha256` | Контрольная сумма каждого архива с его исходным именем. |

Пакеты Mac также содержат `BUILD.json`, внутренний `SHA256SUMS`, адреса записи
прошивки и минимальную версию macOS, извлечённую из исполняемого файла.
Приложение устанавливается локально по [руководству](hardware.md#install-a-prebuilt-package).
Каждый архив приложения содержит `THIRD-PARTY-NOTICES.md` для Rust-крейтов в
исполняемом файле этой платформы и уведомления стандартной библиотеки Rust; пакеты
для Mac добавляют скомпонованные библиотеки прошивки. Их создаёт
`scripts/third-party-notices.py` из `Cargo.lock`, исходников крейтов и карты
компоновки прошивки; упаковка запускает его сама.
Сборки не нотарифицированы с Developer ID. На Linux приложение собирают из
исходников; процесса публикации в Homebrew или crates.io нет.

Трей на Linux использует GTK 3 через `tao` и `tray-icon`. Rust-привязки GTK 3
(0.18) больше не поддерживаются и подтягивают `glib` 0.18, затронутый
[RUSTSEC-2024-0429](https://rustsec.org/advisories/RUSTSEC-2024-0429.html)
(некорректный `VariantStrIter`, который BroGlow не вызывает; исправлено только в `glib` 0.20,
который привязки GTK 3 использовать не могут), и неподдерживаемый крейт сборки
`proc-macro-error` ([RUSTSEC-2024-0370](https://rustsec.org/advisories/RUSTSEC-2024-0370.html)).
Сборки для Mac и Windows этих крейтов не содержат. Готовые сборки для Linux не публикуются.

<a name="python-version"></a>

## Версия Python

Релизы, CI прошивки и Pages используют **Python 3.14**. Корневые инструменты Python
и прошивки берутся из `pyproject.toml` + `uv.lock`; сборки прошивки используют
**PlatformIO Core 6.2.0** и esptool **5.4.0**.

Для генерации корпуса нужны **macOS 15 на Apple Silicon с Python 3.14**
(`macos-15` в релизном CI). Другие платформы могут создавать отличающиеся байты STL;
принимайте новые хеши только после настоящих проверок слайсером на этой платформе.

<a name="before-the-first-public-release"></a>

## Перед первым публичным релизом

1. Выберите репозиторий проекта и проверьте `git remote -v` перед отправкой.
   Явно настройте предполагаемое место публикации.
2. Публикуйте [наши изображения](media.md), добавляйте лицензию MIT и
   уведомления зависимостей. Проверьте устаревшие материалы в старых коммитах
   Git перед открытием истории; исключения архивов в `.gitattributes` не
   переписывают историю. При необходимости используйте проверенный снимок
   исходников или отдельно спланированную очистку истории.
   Пересоберите релизные пакеты из текущих исходников.
3. Закоммитьте запланированные изменения приложения, прошивки, документации
   и процессов CI. Проверьте `git status --short`: релизная упаковка отклоняет
   рабочий каталог с незакоммиченными изменениями. Включите принятые исходники
   корпуса, инструкции и проверенные свидетельства слайсера в релизный коммит;
   комплекты для печати генерируйте из этих исходников и оставляйте игнорируемыми.
4. Выполните проверки ниже. На новой машине всё равно нужны обычное разрешение
   macOS и реальная локальная задача coding-агента для проверки доставки хуков.

<a name="build-a-draft-release"></a>

## Подготовка черновика релиза

Подготовленная версия в `Cargo.toml` и `Cargo.lock` — **1.0.0**. Релизный тег
**v1.0.0** должен указывать на проверенный релизный коммит. Для следующих
релизов обновляйте обе записи версии перед созданием тега.
Проверьте исходники и сайт командами из
[CONTRIBUTING.ru.md](../../../CONTRIBUTING.ru.md#build-and-test) и
[site/README.md](../../README.ru.md#check-changes).

После проверки коммита и места назначения явно создайте тег и отправьте
изменения. Замените `YOUR_REMOTE` выбранным удалённым репозиторием проекта:

```bash
git tag v1.0.0
uv run --frozen python scripts/package-macos.py --release-tag v1.0.0 --check-only
git push YOUR_REMOTE HEAD
git push YOUR_REMOTE v1.0.0
```

Отправляйте только этот тег. Каждый отправленный тег `v*` запускает процесс
**Release**, а унаследованные теги `v0.*` не проходят его проверку версии,
поэтому не используйте `git push --tags`.

Процесс **Release** проверяет тег, версию и отсутствие незакоммиченных
изменений, запускает переиспользуемый набор CI, собирает на нативных
исполнителях Apple Silicon и Intel, а также Windows. Задание `source` на
Apple Silicon `macos-15` устанавливает закреплённые CAD-зависимости Python и
генерирует все печатные STL и четыре STEP-вида из выбранного тега. Он выполняет полные CAD/mesh-проверки, пересоздаёт размерные
изображения, сверяет точные хеши STL с проверенными свидетельствами слайсера,
собирает и проверяет комплекты, прикладывает
`dist/enclosure/broglow-enclosure-magnetic-vVERSION.zip` (рекомендуемый) и
`dist/enclosure/broglow-enclosure-vVERSION.zip` (клеевой), каждый со своим `.sha256`.
Финальная проверка чистоты исходников защищает отслеживаемые файлы от изменений
сгенерированными отчётами. Процесс проверяет каждый ожидаемый архив приложения
и корпуса с контрольной суммой, затем создаёт **черновик GitHub Release**.
CI включает форматирование, lint и тесты Rust, интеграцию JavaScript, проверки
прошивки на компьютере, форматирование прошивки и обе сборки C3.
Перед упаковкой релиз также запускает проверки процесса **Website**, не
развёртывая сайт.

Перед нажатием **Publish release** в GitHub:

- Скачайте подходящий архив Mac и его контрольную сумму из черновика.
  Пройдите приложенное руководство от распаковки до установки; проверьте
  `--version`, сервис при входе в систему, разрешение Bluetooth, сопряжение
  и реальную задачу агента.
- Проверьте `BUILD.json`, содержимое архивов и контрольные суммы. Пакеты
  приложения и ZIP корпуса скачиваются отдельно; исключите референсные
  изображения, файлы восстановления и локальные настройки пользователя
  из всех артефактов.
- Укажите, на каких машинах и какое поведение лампы проверялось фактически.
  Локальная приёмка сейчас охватывает Apple Silicon; успешная сборка Intel
  не является проверкой на оборудовании Intel. Явно укажите непроверенные
  платформы и ограничения первого релиза.
- Проверьте сформированные заметки и выберите подходящую отметку релиза
  или предварительного релиза. Именно публикация черновика делает бинарные
  загрузки общедоступными.

[Список приёмочных проверок](hardware.md#physical-and-background-service-acceptance)
разделяет сборку, доставку статуса сервисом, физические светодиоды и проверку
корпуса. Не перепрошивайте работающую плату только ради проверки процесса выпуска.

<a name="package-locally-without-publishing"></a>

## Локальная упаковка без публикации

По умолчанию генерируется рекомендуемый магнитный комплект. Его самостоятельная
инструкция — `models/magnetic/GUIDE_ROUND3X2.md`: состав печати, вклейка магнитов
и генерация из исходников. Команда:

```bash
uv run --no-project --python 3.14 --with-requirements models/broglow/requirements.txt \
  python scripts/package-enclosure.py --variant magnetic
```

Результат — `dist/enclosure/broglow-enclosure-magnetic-vVERSION.zip` и его
`.sha256`; изолированная генерация выполняется в `dist/enclosure/magnetic-build/source/`.
Проверяются и экспортируются только текущий вариант и детали 01–05; купонов,
нарезанных под принтер 3MF/G-code нет. Хеши всех пяти STL должны совпадать с
сохранённой проверкой слайсера. Диаметр кармана 3,05 мм подтверждён примеркой;
окончательная глубина 2,30 мм и удержание сборки ещё не проверены физически.

Релизный CI запускает `--variant magnetic` и `--variant glued`, прикладывая оба
ZIP и контрольные суммы к одному черновику релиза. Процедура ниже описывает
прежнюю **клеевую альтернативу**; передавайте `--variant glued` явно.


Используйте готовую [процедуру ручной генерации](../../../models/broglow/PRINT_GUIDE.md#generate-from-source)
или эквивалентный [запрос агенту](../../../models/broglow/PRINT_GUIDE.md#agent-generation).
Оба варианта запускают `scripts/package-enclosure.py --variant glued` на macOS 15 Apple Silicon
с Python 3.14 и закреплёнными `models/broglow/requirements.txt`; плата, PlatformIO
и скилл агента не нужны.
Команда генерирует геометрию, размерные изображения и полную проверку мешей
в изолированном дереве `dist/enclosure/source/`, затем использует
`package_prints.py` для проверки свидетельств слайсера и содержимого архивов.
Проверенные исходные отчёты остаются неизменными.

Разовые отчёты инспекции CAD и задания снимков для отдельных версий не входят
во входные данные сборки; храните их в игнорируемом `dist/enclosure/`, вне Git.
Сборка заново создаёт `parts.json` и `validation.json` в изолированном дереве.
Сохраняйте проверенный `slicer-validation.json`: упаковка сверяет его хеши STL,
поскольку генерация геометрии не запускает внешний слайсер повторно.

Весь каталог `models/broglow/preview/` должен оставаться игнорируемым и
неотслеживаемым, включая рендеры, размерные схемы и задания рендера. Храните в Git
выбранные ресурсы приложения/сайта и проверенные данные валидации. Генерируйте
схемы для релиза в `dist/enclosure/`.

Полный `dist/enclosure/broglow-enclosure-v1.0.0.zip` и соответствующий `.sha256`
прикладываются к релизу корпуса. Там же находятся `broglow-print-pack.zip`,
`broglow-compact-STL.zip` и `broglow-USB-fit-test.zip` для локального использования
или дополнительных загрузок релиза. `--output-dir PATH` выбирает другую папку;
она тоже должна игнорироваться. Для CI или репетиции релиза используйте чистый
checkout с соответствующим тегом:

```bash
uv run --no-project --python 3.14 --with-requirements models/broglow/requirements.txt \
  python scripts/package-enclosure.py --variant glued --release-tag v1.0.0
```

Строгий релизный режим проверяет тег, версию и чистоту исходников до генерации.
Несовпадение хеша слайсера останавливает сборку: исследуйте закреплённый набор
инструментов и выполните настоящую нарезку изменённых мешей перед обновлением
проверенных свидетельств. Проверки геометрии не заменяют нарезку, и ни одна из
них не подтверждает физическую посадку напечатанных деталей.

На Mac соответствующей архитектуры сначала соберите приложение и рабочий
образ C3:

```bash
cargo build --release --locked
uv run --frozen flash --build-only
uv run --frozen python scripts/package-macos.py
```

Получатся архив с меткой времени и `.sha256` в игнорируемом каталоге `dist/`.
Сам упаковщик ничего не собирает, не устанавливает, не прошивает и не
публикует. Локальные пакеты могут использовать каталог с незакоммиченными
изменениями; `BUILD.json` фиксирует это и хеши входных файлов сборки.
Используйте `--release-tag vVERSION` только для чистого каталога и
соответствующего коммита с тегом; этот режим использует постоянное релизное
имя файла и отказывается перезаписывать существующий архив.

<a name="publish-the-website"></a>

## Публикация сайта

Следуйте [инструкции по сайту](../../README.ru.md#publish-to-github-pages):
включите GitHub Pages с источником **GitHub Actions**, затем запустите
**Website** на ветке по умолчанию. Процесс получает URL репозитория из GitHub,
собирает и проверяет главную страницу и двуязычное руководство, затем
загружает только `site/_pages/`.

Главная страница находится по адресу публикации, руководства — в `docs/`
и `docs/ru/`. Пути работают как в корне домена, так и с префиксом репозитория.
Отправка изменений сайта или документации в `master` автоматически публикует
их; при необходимости измените фильтр ветки. PR проходят сборку и проверку
без публикации. Свой домен настраивается в Pages; правила окружения могут
потребовать подтверждения в GitHub.

После публикации откройте английское и русское руководства на сайте и
пройдите от ссылки на релиз до его контрольной суммы. Руководство ссылается
на Releases этого репозитория и предлагает сборку из исходников до первого
полного релиза. В нём есть отдельная загрузка корпуса, а изображения изделия
подписаны как CAD-рендеры.

Локальные проверки не подтверждают права GitHub, успех облачных исполнителей,
работу опубликованного Pages или установку на другом Mac. Проверьте это при
первом черновике релиза и публикации; сама подготовка ничего не публикует.

# Выпуск и публикация

Это инструкция для сопровождающих, работающих с исходниками. Упомянутые ниже
файлы `site/` и `.github/` не входят в готовые пакеты приложения.

Выпуск приложения/прошивки и публикация сайта используют отдельные процессы
GitHub Actions. Файлы STL и STEP распространяются только внутри ZIP-архивов
корпуса, приложенных к релизу; все сгенерированные файлы оставляйте
игнорируемыми и вне Git (см. [CONTRIBUTING.ru.md](../../../CONTRIBUTING.ru.md)).

<a name="distribution"></a>

## Распространение

| Загрузка | Содержимое |
| --- | --- |
| `broglow-vVERSION-aarch64-apple-darwin.tar.gz` | Приложение для Apple Silicon, прошивка C3 и её исходники, руководство, лицензии и контрольные суммы. |
| `broglow-vVERSION-x86_64-apple-darwin.tar.gz` | Такой же пакет с нативным приложением для Mac на Intel. |
| `broglow-vVERSION-x86_64-pc-windows-msvc.tar.gz` | Графическое приложение в трее и CLI для Windows в `broglow.exe`, с поддержкой лампы по USB, лицензией и уведомлениями о сторонних компонентах; без установщика, BLE, прошивки и руководств. |
| `broglow-enclosure-magnetic-vVERSION.zip` | Рекомендуемый съёмный корпус: пять рабочих деталей STL/STEP, виды сборки, исходники, инструкция и отчёты; четыре магнита Ø3×2 мм N52. |
| `broglow-enclosure-vVERSION.zip` | Клеевая альтернатива: STL и STEP, исходники CAD, руководство и отчёты проверок. |
| Соответствующий `.sha256` | Контрольная сумма каждого архива с его исходным именем. |

Пакеты Mac также содержат `BUILD.json`, внутренний `SHA256SUMS`, адреса записи
прошивки и минимальную версию macOS, извлечённую из исполняемого файла.
Приложение устанавливается по приложенному [руководству](hardware.md#install-a-prebuilt-package).
Каждый архив приложения содержит `THIRD-PARTY-NOTICES.md` для Rust-крейтов в
исполняемом файле этой платформы и уведомления стандартной библиотеки Rust; пакеты
для Mac добавляют скомпонованные библиотеки прошивки. Их создаёт
[`scripts/third-party-notices.py`](../../../scripts/third-party-notices.py) из
`Cargo.lock`, исходников крейтов и карты компоновки прошивки; упаковка запускает
его сама. Сборки не подписаны сертификатом Developer ID и не нотаризованы Apple.
На Linux приложение собирают из исходников; процесса публикации в Homebrew или
crates.io нет.

Готовые сборки для Linux не публикуются; о предупреждениях безопасности GTK 3
для трея на Linux см. [CONTRIBUTING](../../../CONTRIBUTING.ru.md#development-setup).

<a name="python-version"></a>

## Версия Python

Релизы, CI прошивки и Pages используют **Python 3.14**. Корневые инструменты Python
и прошивки берутся из `pyproject.toml` + `uv.lock`; сборки прошивки используют
**PlatformIO Core 6.2.0** и esptool **5.4.0**.

Проверенные хеши STL получены на **macOS 15 на Apple Silicon с Python 3.14**
(`macos-15` в релизном CI). На других платформах байты STL могут отличаться, и
проверка хешей не пройдёт; принимайте новые хеши только после настоящей нарезки
в слайсере на этой платформе.

<a name="before-the-first-public-release"></a>

## Перед первым публичным релизом

1. Сделайте это до первого `git push`. Убедитесь, что `package.repository` в
   `Cargo.toml` указывает на публичный репозиторий (на него ссылается
   документация), добавьте его как удалённый и проверьте `git remote -v`:

    ```bash
    git remote add YOUR_REMOTE {{ repo_url }}
    git remote -v
    ```

2. Используйте только [собственные изображения](media.md) и добавьте `LICENSE`
   (MIT) и уведомления зависимостей.
3. Отправка ветки публикует всю её историю. Проверьте устаревшие материалы в
   старых коммитах перед открытием истории; исключения архивов в
   `.gitattributes` не переписывают историю. При необходимости используйте
   проверенный снимок исходников или отдельно спланированную очистку истории.
   Старые теги `v0.*` остаются локальными, пока их не отправят по имени.
4. Закоммитьте запланированные изменения приложения, прошивки, документации
   и процессов CI. Проверьте `git status --short`: релизная упаковка отклоняет
   рабочую копию с незакоммиченными изменениями. Включите принятые исходники
   корпуса, инструкции и результаты проверки в слайсере (`slicer-validation.json`)
   в релизный коммит; комплекты для печати генерируйте из этих исходников и
   оставляйте игнорируемыми.
5. Выполните проверки ниже. На новой машине всё равно нужны обычное разрешение
   macOS и реальная локальная задача агента для проверки доставки хуков.

<a name="build-a-draft-release"></a>

## Подготовка черновика релиза

Подготовленная версия в `Cargo.toml` и `Cargo.lock` — **1.0.0**. Релизный тег
**v1.0.0** должен указывать на проверенный релизный коммит.
Проверьте исходники и сайт командами из
[CONTRIBUTING.ru.md](../../../CONTRIBUTING.ru.md#build-and-test) и
[инструкции по сайту](../../README.ru.md#check-changes).

После проверки коммита и места назначения явно создайте тег и отправьте
изменения. Замените `YOUR_REMOTE` удалённым репозиторием, добавленным выше:

```bash
git tag v1.0.0
uv run --frozen python scripts/package-macos.py --release-tag v1.0.0 --check-only
git push YOUR_REMOTE HEAD:master
git push YOUR_REMOTE v1.0.0
```

Если проверка не прошла (незакоммиченные изменения или несовпадение версии),
удалите локальный тег командой `git tag -d v1.0.0`, исправьте проблему и
повторите. Отправка в `master` запускает CI, а если она меняет сайт,
документацию, модели или `Cargo.toml`, ещё и автоматически публикует сайт.

Отправляйте только этот тег, по имени. Каждый отправленный тег `v*` запускает
процесс **Release**, а унаследованные теги `v0.*` не проходят его проверку
версии, поэтому никогда не используйте `git push --tags`. Для следующего релиза
поднимите `version` в `Cargo.toml` и `Cargo.lock`, закоммитьте, затем создайте и
отправьте только тег этой версии: `git push YOUR_REMOTE vX.Y.Z`.

Процесс **Release** выполняется в таком порядке:

1. Задание `source` на Apple Silicon `macos-15` запускает тесты упаковки и
   проверяет тег, версию и отсутствие незакоммиченных изменений. Оно
   устанавливает закреплённые CAD-зависимости Python и генерирует оба варианта
   корпуса из тега:
    - **Магнитный**: пять рабочих деталей с файлами STL и STEP и виды сборки.
    - **Клеевой**: все печатные STL и четыре STEP-вида, полные CAD/mesh-проверки
      и размерные изображения.

    Для обоих вариантов точные хеши STL сверяются с проверенными результатами
    проверки в слайсере, и создаётся ZIP со своим `.sha256`. Затем задание
    проверяет актуальность экспорта веб-модели
    (`scripts/export-web-model.py --check`), а финальная проверка чистоты
    исходников защищает отслеживаемые файлы от изменений сгенерированными отчётами.
2. Затем запускаются переиспользуемый набор CI и проверки процесса **Website**,
   без развёртывания сайта. CI включает форматирование, lint и тесты Rust,
   форматирование Python и прошивки, интеграцию JavaScript, проверки упаковки и
   сгенерированных файлов, проверки прошивки на компьютере и обе сборки C3.
3. Когда обе проверки пройдены, нативные исполнители Apple Silicon и Intel
   собирают и упаковывают приложение для Mac и прошивку C3, а исполнитель
   Windows собирает приложение в трее и CLI.
4. Последнее задание проверяет каждый ожидаемый архив, его контрольную сумму и
   уведомления о сторонних компонентах, затем создаёт **черновик GitHub
   Release**. К нему прикладываются только архивы и их файлы `.sha256`.

Перед нажатием **Publish release** в GitHub:

- Скачайте подходящий архив Mac и его контрольную сумму из черновика.
  Пройдите приложенное руководство от распаковки до установки; проверьте
  `--version`, сервис при входе в систему, разрешение Bluetooth, сопряжение
  и реальную задачу агента.
- Проверьте `BUILD.json`, содержимое архивов и контрольные суммы. Пакеты
  приложения и ZIP корпуса скачиваются отдельно; исключите референсные
  изображения, файлы восстановления и локальные настройки пользователя
  из всех артефактов.
- Укажите, на каких машинах и какое поведение лампы проверялось фактически.
  Локальная приёмка сейчас охватывает Apple Silicon; успешная сборка Intel
  не является проверкой на оборудовании Intel. Явно укажите непроверенные
  платформы и ограничения первого релиза.
- Проверьте сформированные заметки и выберите подходящую отметку релиза
  или предварительного релиза. Именно публикация черновика делает бинарные
  загрузки общедоступными.

[Список приёмочных проверок](hardware.md#physical-and-background-service-acceptance)
в руководстве разделяет сборку, доставку статуса сервисом, физические светодиоды и проверку
корпуса. Не перепрошивайте работающую плату только ради проверки процесса выпуска.

<a name="package-locally-without-publishing"></a>

## Локальная упаковка без публикации

Релизный CI упаковывает оба варианта корпуса и прикладывает оба ZIP с
контрольными суммами к одному черновику релиза. Локально каждый пакет
собирается отдельно. [`scripts/package-enclosure.py`](../../../scripts/package-enclosure.py)
по умолчанию собирает магнитный вариант. `--output-dir PATH` выбирает другую
папку; она тоже должна игнорироваться. Для репетиции релиза используйте чистую
рабочую копию с соответствующим тегом и добавьте `--release-tag vVERSION`: этот
строгий режим проверяет тег, версию и чистоту исходников до генерации.

<a name="package-magnetic-enclosure"></a>

### Магнитный корпус

[Руководство по печати магнитного корпуса](printing.md) описывает состав печати,
вклейку магнитов и генерацию из исходников. Команда:

```bash
uv run --no-project --python 3.14 --with-requirements models/broglow/requirements.txt \
  python scripts/package-enclosure.py --variant magnetic
```

Результат — `dist/enclosure/broglow-enclosure-magnetic-vVERSION.zip` и его
`.sha256`; изолированная генерация выполняется в `dist/enclosure/magnetic-build/source/`.
Экспортируются только рабочие детали 01–05; купонов и нарезанных под принтер
3MF/G-code нет. Хеши всех пяти STL должны совпадать с сохранёнными результатами
проверки в слайсере.

<a name="package-glued-enclosure"></a>

### Клеевой корпус

Передавайте `--variant glued` явно. Для локальной сборки только клеевого корпуса
(без `--release-tag`, не репетиция релиза) используйте
[процедуру ручной генерации](../../../models/broglow/PRINT_GUIDE.md#generate-from-source)
или эквивалентный [запрос агенту](../../../models/broglow/PRINT_GUIDE.md#agent-generation).
Оба варианта запускают скрипт упаковки на macOS 15 Apple Silicon с Python 3.14 и
закреплёнными [`models/broglow/requirements.txt`](../../../models/broglow/requirements.txt);
плата, PlatformIO и скилл агента не нужны. Для репетиции релиза:

```bash
uv run --no-project --python 3.14 --with-requirements models/broglow/requirements.txt \
  python scripts/package-enclosure.py --variant glued --release-tag vVERSION
```

Команда генерирует геометрию, размерные изображения и полную проверку мешей
в изолированном дереве `dist/enclosure/source/`, затем использует
[`package_prints.py`](../../../models/broglow/package_prints.py) для сверки с
результатами проверки в слайсере и проверки содержимого архивов. Проверенные
исходные отчёты остаются неизменными.

`dist/enclosure/broglow-enclosure-vVERSION.zip` (копия `broglow-print-pack.zip`)
и его `.sha256` — файлы релиза для клеевого варианта. `broglow-compact-STL.zip` и
`broglow-USB-fit-test.zip` в том же каталоге предназначены для локального
использования; процесс **Release** их не загружает.

Весь каталог `models/broglow/preview/` должен оставаться игнорируемым и
неотслеживаемым, включая рендеры, размерные схемы и задания рендера. Храните в Git
выбранные ресурсы приложения/сайта и проверенные данные валидации. Генерируйте
схемы для релиза в `dist/enclosure/`.

Разовые отчёты инспекции CAD и задания снимков для отдельных версий не входят
во входные данные сборки; храните их в игнорируемом `dist/enclosure/`, вне Git.
Сборка заново создаёт `parts.json` и `validation.json` в изолированном дереве.
Сохраняйте проверенный [`slicer-validation.json`](../../../models/broglow/slicer-validation.json):
упаковка сверяет его хеши STL, поскольку генерация геометрии не запускает
внешний слайсер повторно.

Несовпадение хеша STL останавливает сборку: исследуйте закреплённый набор
инструментов и выполните настоящую нарезку изменённых мешей перед обновлением
проверенных результатов. Проверки геометрии не заменяют нарезку, и ни одна из
них не подтверждает физическую посадку напечатанных деталей.

<a name="package-mac-app"></a>

### Пакет приложения для Mac

На Mac соответствующей архитектуры сначала соберите приложение и рабочий
образ C3:

```bash
cargo build --release --locked
uv run --frozen flash --build-only
uv run --frozen python scripts/package-macos.py
```

Получится архив с меткой времени и файл `.sha256` в игнорируемом каталоге `dist/`.
Сам упаковщик ничего не собирает, не устанавливает, не прошивает и не
публикует. Локальные пакеты могут использовать рабочую копию с незакоммиченными
изменениями; `BUILD.json` фиксирует это и хеши входных файлов сборки.
Используйте `--release-tag vVERSION` только для чистой рабочей копии и
соответствующего коммита с тегом; этот режим использует постоянное релизное
имя файла и отказывается перезаписывать существующий архив.

<a name="publish-the-website"></a>

## Публикация сайта

Следуйте [инструкции по сайту](../../README.ru.md#publish-to-github-pages), затем
выполните проверку после публикации.

После публикации откройте английское и русское руководства на сайте и
пройдите от ссылки на релиз до его контрольной суммы. Ссылки на загрузки ведут
на Releases этого репозитория; пока релиз не опубликован, руководство предлагает
собрать приложение из исходников — после публикации проверьте, что ссылки
работают. В руководстве есть отдельная загрузка корпуса, а изображение изделия
на главной странице подписано как рендер.

Локальные проверки не подтверждают права GitHub, успех облачных исполнителей,
работу опубликованного Pages или установку на другом Mac. Проверьте это при
первом черновике релиза и публикации; сама подготовка ничего не публикует.

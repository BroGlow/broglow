# broglow

Следуйте границам самостоятельного продукта из [AGENTS.ru.md](AGENTS.ru.md).

Для установки из пакета или исходников, подключения платы и проверки работающей
службы Mac начните с [руководства для агента](site/guide/ru/hardware.md#agent-runbook).

Один исполняемый файл на Rust отслеживает сессии
[Claude Code](https://claude.ai/code) в реальном времени. У него три режима:

- **Панель TUI** (`broglow`) — таблица ratatui со всеми сессиями и их текущими статусами.
- **Фоновая служба строки меню / системного трея** (`broglow menubar`) — цветной
  индикатор общего состояния сессий; автоматически запускается при входе.
- **Обработчик хуков** (`broglow hook`) — вызывается хуками жизненного цикла
  Claude Code и записывает статус каждой сессии. Заменяет старый скрипт на
  bash+jq; не зависит от оболочки или `jq`.

По желанию общее состояние передаётся через последовательный порт USB или,
на macOS, через BLE в прошивку ESP32-C3 SuperMini из этого репозитория.
Изменение аппаратуры, прошивка, настройка Bluetooth, развёртывание и результаты
приёмки описаны в [руководстве по оборудованию](site/guide/ru/hardware.md).

Поддерживаются macOS, Windows и Linux. Лицензия MIT.

<a name="build-test-install"></a>

## Сборка / тестирование / установка

При изменении исходников следуйте [CONTRIBUTING.ru.md](CONTRIBUTING.ru.md): там
описаны окружение, форматирование, хуки и проверки. [Команды сборки и тестирования](CONTRIBUTING.ru.md#build-and-test)
общие для людей и агентов, участвующих в разработке.

`broglow install` идемпотентна и также запускает или перезапускает фоновую
службу трея. Повторяйте её после `cargo install`, чтобы служба использовала
новый исполняемый файл. На macOS она устанавливает `~/Applications/BroGlow.app`
и перезагружает существующий LaunchAgent (`io.github.broglow.menubar`) через
`launchctl bootout`/`bootstrap`/`kickstart`. Перед развёртыванием проверьте
установленную службу и сохраните посторонние хуки и настройки.

**Всегда повторно развёртывайте приложение после изменений кода.** Завершайте
изменения кода в этом репозитории обновлением приложения, уже работающего на
этом компьютере, чтобы проверить его вживую:

```bash
cargo install --path . && broglow install
```

Для живых проверок обновляйте установленную службу. Блокировка на всё время
жизни процесса не допускает второй экземпляр трея macOS; отдельная блокировка
BLE не даёт поиску устройств и рабочему процессу использовать радио одновременно.
Сборка не подтверждает выдачу разрешений или работу платы: фиксируйте эти
приёмочные проверки отдельно.

<a name="subcommands-srcmainrs"></a>

## Подкоманды (src/main.rs)

| Команда | Назначение |
|---|---|
| *(без команды)* | Запуск панели TUI (`run_tui`); при первом запуске на ненастроенном компьютере установка выполняется автоматически (см. особенности ниже) |
| `install` / `uninstall` | Хуки и автозапуск для платформы (launchd / ключ Run реестра / автозапуск XDG) |
| `menubar` | Запуск службы трея на переднем плане |
| `led [--port]` | Передача статуса на LED ESP32 на переднем плане для отладки |
| `ble pair [--port]` | Определение прошивки BroGlow по USB, открытие сопряжения и сохранение соответствующего BLE ID; шифрование и подтверждение macOS обрабатывает работающий трей |
| `ble scan/add/remove/list/on/off/usb/status` | Поиск устройств, сохранение/удаление CoreBluetooth ID, список состояний ламп, включение/отключение выбранного транспорта, возврат к USB или проверка рабочего процесса |
| `hook` *(скрытая)* | Обработчик хуков Claude Code; читает одно событие JSON из stdin |
| `event` *(скрытая)* | Обработчик нормализованных событий других агентов (opencode); читает одно событие JSON из stdin |
| `codex-hook` *(скрытая)* | Адаптер Codex: читает из stdin одно событие хука в формате Claude и преобразует его в нормализованное событие |
| `copilot-hook <event>` *(скрытая)* | Адаптер Copilot: читает из stdin данные одного события (имя события передаётся через argv) и преобразует его в нормализованное событие |
| `name <id> <transcript>` *(скрытая)* | Отдельный процесс автоматического именования; задаёт название сессии без названия через CLI `claude`, а при ошибке — по первому запросу |

<a name="module-map-src"></a>

## Карта модулей (src/)

- **main.rs** — разбор CLI, подготовка и завершение TUI (обработчик panic
  восстанавливает терминал), вся логика установки/удаления и автозапуска по платформам.
- **hook.rs** — обработчики `hook`, `event`, `codex-hook`, `copilot-hook` и `name`.
  Преобразует хуки Claude и независимые от агента нормализованные действия
  `event` в `Status`, выполняет чтение, изменение и запись `state.json` под
  блокировкой через общий помощник `update_state`, берёт названия сессий Claude
  из собственной записи `custom-title` в транскрипте, запускает отдельный процесс
  именования при первом `Stop` сессии без названия. `run_event` принимает события разных агентов;
  `run_codex_hook` и `run_copilot_hook` в том же процессе преобразуют формат
  Claude у Codex и отдельные события Copilot в те же действия — см. раздел
  «Адаптеры разных агентов» ниже.
- **codex.rs** — всё, что относится к Codex, за адаптером `codex`: пути
  `$CODEX_HOME`, слияние hooks.json с сохранением позиций (Codex доверяет хукам
  по хешу содержимого и позиции — нельзя переставлять чужие группы или писать
  в config.toml Codex), названия задач из `session_index.jsonl`, различение exec
  и интерактивного режима по `session_meta` журнала, извлечение первого
  введённого запроса для резервного названия.
- **copilot.rs** — всё, что относится к Copilot, за адаптером `copilot`: пути
  `$COPILOT_HOME` и полностью принадлежащий приложению файл регистрации
  `hooks/broglow.json` (по одной группе команд на событие жизненного цикла;
  имя события встроено в argv, поскольку Copilot не передаёт его в данных;
  принадлежность определяется строкой команды `copilot-hook` — в JSON нет
  комментариев для служебной отметки).
- **state.rs** — типы `HookState`/`SessionStatus`/`Status`, включая необязательное
  поле `harness`: отсутствует для Claude, `"opencode"` для opencode; чтение и
  запись `state.json` через атомарные временный файл и переименование; общая
  `.state.lock` (`acquire_state_lock`); перевод в `Done` через `reap_ended_sessions`
  при завершении процесса (`terminal::is_alive`) и страховочная очистка через
  24 часа; сводное состояние `Aggregate` (Red/Yellow/Green/None).
- **session.rs** — превращает состояние хуков в `DisplaySession` для TUI:
  отображаемые имена, порядок сортировки и пять последних завершённых сессий.
  Все имена приходят из хуков.
- **config.rs** — `~/.claude/broglow/config.json`: явное включение LED,
  `led_transport` по умолчанию USB, необязательный `led_port`, сохранённые
  `ble_peripherals`, `yellow_mode` и `show_agent_names` (по умолчанию включено).
  Используйте `ble_ids()`, чтобы удалять
  дубликаты сохранённых `ble_peripherals`. При выборе лампы
  сохраняйте посторонние и неизвестные настройки.
- **app.rs** — цикл событий TUI: наблюдение за файлом, обновление каждые 5 секунд,
  обработка клавиш, уведомления.
- **ui.rs** — отрисовка таблицы и строки состояния через ratatui. 24-битные цвета
  используются, только если `COLORTERM` равен `truecolor`/`24bit`; иначе каждый кадр
  переводит их в палитру xterm из 256 цветов, потому что Terminal.app до macOS 26
  читает компоненты RGB как отдельные коды SGR.
- **menubar.rs** — значок и меню трея (цикл событий tao/tray-icon), запуск потока
  фонового управления LED.
- **led.rs** — обнаружение и драйвер USB, преобразование сводного состояния в
  байт, выбор транспорта и актуальный межпроцессный статус в `lamp-status.json`.
- **ble.rs** — настройка через USB, поиск и выбор устройств, рабочий процесс BLE на macOS:
  поиск по сервису, независимые подключения к каждой сохранённой доступной лампе,
  записи с подтверждением, периодические обновления и переподключение. Отсутствие
  одной лампы не должно мешать обновлению другой. USB-команда `pair` требует
  точного совпадения INFO перед PAIR и проверяет сервис и полный шестибайтовый
  базовый MAC в данных производителя (`0xffff`). Tray проверяет USB каждые пять
  секунд и делает одну попытку настройки на новое подключение; `usb_lamps` хранит
  проверенные платы, сохраняя Disable/Forget после перезапуска. Сохраняйте точную
  проверку идентификаторов, блокировки порта/обработчика, откат при ошибке и согласие macOS.
  Сохраняйте
  фиксированную версию btleplug 0.13.1: она исправляет потерю ошибок записи
  CoreBluetooth NSError при сопряжении на macOS. Увеличение тайм-аута хоста
  не продлевает системный запрос сопряжения macOS (наблюдалось около 30 секунд).
- **notification.rs** — уведомления рабочего стола (`osascript` на macOS,
  `notify-rust` на остальных платформах).
- **spawn.rs** — флаги запуска отдельного дочернего процесса без окна только
  для Windows; на остальных платформах ничего не делают.
- **terminal.rs** — переход к окну по нажатию: `capture` записывает, в каком
  окне терминала или приложении работает сессия (переменные окружения и обход
  дерева процессов, сохранение для каждой сессии в `state.json`); `focus`
  затем поднимает это окно (сопоставление вкладки по tty через AppleScript на
  macOS, `SetForegroundWindow` для родительского окна на Windows, xdotool на
  Linux). Используется строками сессий во всплывающем окне, меню трея Linux
  и клавишей `↵` в TUI. `host` относит ту же информацию к приложению агента,
  терминалу или IDE и даёт короткое имя («Claude app», «Ghostty», «VS Code») для
  значка места запуска во всплывающем окне и столбца HOST в TUI; пакет
  приложения важнее устаревших переменных терминала, а сессия Codex без данных
  о терминале считается приложением Codex, как и в `focus`.

<a name="data-flow"></a>

## Поток данных

Claude Code вызывает хук → `broglow hook` читает JSON события из stdin →
обновляет запись сессии в `~/.claude/broglow/state.json`. TUI и служба трея
наблюдают за этим файлом через `notify` и перерисовываются при изменениях.
Соответствие событий статусам:

- `SessionStart` / `UserPromptSubmit` / `PreToolUse` → `Active`
- `Stop` → `Inactive`
- `Notification` → `NeedsHelp` (кроме `idle_prompt`, которое игнорируется)
- `SessionEnd` → `Done`

Общий цвет значка и LED: любое `NeedsHelp` → красный. Далее смешанные состояния
определяет `yellow_mode` из настроек всплывающего окна: `any_inactive` (по
умолчанию) — любое `Inactive` даёт жёлтый, иначе любое `Active` даёт зелёный;
`active_wins` — любое `Active` даёт зелёный, жёлтый появляется только тогда,
когда все живые сессии простаивают. Нет живых сессий → None (серый).
См. `state::aggregate`.

<a name="multi-harness-adapters-opencode-and-future-ones"></a>

## Адаптеры разных агентов (opencode и будущие)

Сессии других coding-агентов попадают в *тот же* `state.json` и отображаются
в TUI, трее, общем состоянии и LED без изменения читающих компонентов:
все читающие компоненты показывают сессии из состояния хуков, какой бы агент их
ни записал. Адаптер намеренно минимален:

- **`broglow event`** (`hook::run_event`) — точка приёма. Читает из stdin одно
  *нормализованное* событие JSON: `{ harness, event, session_id, title?, directory? }`.
  Действия статуса не зависят от агента: все адаптеры передают одинаковую
  структуру (opencode через JS-плагин, Codex и Copilot через встроенные
  `codex-hook` / `copilot-hook`):

  | Действие | `Status` |
  |---|---|
  | `working` / `resumed` | `Active` (повторные `working`/`resumed` не записываются, если сессия уже активна и новое название не передано) |
  | `idle` | `Inactive` |
  | `needs_input` | `NeedsHelp` |
  | `ended` | `Done` |
  | `title` | Обновляется только имя, статус не меняется: переименование простаивающей сессии не должно включать зелёный |
  | `reconnected` | Очистка при перезапуске: сессии `Active`/`Inactive` этого агента, чей процесс-владелец завершился или не был определён, → `Done` |

  Неизвестные действия, отсутствие `harness` и отсутствие ID сессии (кроме
  `reconnected`) приводят к пропуску события, а не к ошибке. `harness`
  **обязателен**: нельзя подставлять агента по умолчанию, иначе неверно
  размеченное событие будет принято за его событие. `directory` необязателен
  и, как `name`/`terminal`, сохраняется, если следующее событие его не содержит.
- **`SessionStatus.harness`** отмечает источник
  (`#[serde(default, skip_serializing_if)]`; отсутствие означает Claude).
- **`update_state`** в hook.rs — единственный общий помощник чтения, изменения
  и записи под блокировкой для `run` (хуки Claude), `run_event` и `run_namer`.
  Не реализуйте заново правила блокировки, атомарной записи и запрета записи
  при невозможности прочитать состояние.
- **`harness.rs` — реестр.** Всё, что зависит от агента — обнаружение,
  установка/удаление плагина или хуков, а также значок, название и иконка
  интерфейса — находится в одной таблице `const ADAPTERS: &[Adapter]`.
  `install_all`/`uninstall_all`, вызываемые из `register_hooks`/`uninstall_hooks`,
  и `agent(harness)` обходят эту таблицу. `agent` даёт иконку и название для
  всплывающего окна, столбец AGENT в TUI (название или, если названия отключены,
  метку) и строку меню трея Linux `[cx] Codex · recco`; для Claude — `CLAUDE_LABEL`/`CLAUDE_ICON`/
  `CLAUDE_BADGE` (`cc`). Поэтому
  **добавление Codex/Copilot — одна запись `Adapter` и её встроенный ресурс**, без
  изменений во всех main.rs/session.rs/ui.rs. Каждый новый агент должен иметь
  **уникальный** `badge`; это проверяется тестом, иначе двухсимвольное резервное
  сокращение скрыло бы коллизию `codex`/`copilot` → `"co"`. Также нужны
  уникальные `label` и `icon`. Иконки — наши собственные геометрические знаки, не
  логотипы производителей: только данные пути SVG для обводки 16×16 цветом
  `currentColor`, которые окно помещает лишь в атрибут `d`. Неизвестный агент
  вместо иконки показывает свою метку.
- **`assets/opencode-plugin.js`** встраивается через `include_str!` и при
  установке записывается в глобальный
  `~/.config/opencode/plugins/broglow.js` с абсолютным путём к этому
  исполняемому файлу и его версией. Он работает, даже если broglow нет в PATH
  opencode; безусловная перезапись при каждой установке устраняет расхождение
  версий. Плагин **намеренно не содержит логики**: только нормализует события
  шины opencode в перечисленные действия и запускает `broglow event`,
  не ожидая завершения. Все решения о соответствии событий находятся в Rust
  и проверяются там. Установка выполняется, если найдена папка настроек
  opencode *или* команда `opencode` в PATH; удаление убирает файл только при
  сохранённом заголовке `managed by broglow`. opencode загружает плагины
  при старте, поэтому уже работающие сессии нужно перезапустить.
- **Codex не нужен плагин.** Codex (>= 0.144) сам вызывает хуки в формате
  Claude. Его адаптер регистрирует группы сопоставления `broglow codex-hook`
  в `$CODEX_HOME/hooks.json`, а встроенный обработчик преобразует события:
  `PermissionRequest` → `needs_input` (у Codex нет `Notification`),
  `PostToolUse`/`UserPromptSubmit` → `resumed` (убирает красный после
  подтверждения), `Stop` → `idle` либо `ended` для одноразовых запусков
  `codex exec`, определяемых по `session_meta` журнала. У Codex нет
  `SessionEnd`, поэтому завершение интерактивных сессий определяет очистка по
  PID владельца. Названия берутся из `session_index.jsonl` Codex на границах
  ходов; первый введённый запрос используется один раз как запасной вариант,
  без вызова LLM. Два правила для Codex: при слиянии hooks.json чужие группы
  сопоставления остаются *на своих местах* (доверие Codex зависит от хеша
  содержимого и позиции; пользователь один раз подтверждает новые записи
  broglow через `/hooks` в Codex); broglow никогда не пишет в config.toml
  Codex, который сам Codex перезаписывает во время работы.
- **Copilot не нужен плагин.** GitHub Copilot CLI сам вызывает пользовательские
  хуки жизненного цикла. Любой `*.json` в `$COPILOT_HOME/hooks/` (по умолчанию
  `~/.copilot/hooks/`) может регистрировать команды, поэтому адаптер пишет
  полностью принадлежащий broglow файл `hooks/broglow.json` и не сливает
  записи с чужой конфигурацией. Данные Copilot не содержат имя события,
  поэтому каждая запись запускает `broglow copilot-hook <event>`, а
  обработчик преобразует пару argv/данные в том же процессе:
  `permissionRequest` → `needs_input` (типы `notification` не документированы,
  поэтому они не регистрируются, чтобы не включать красный ошибочно),
  `postToolUse`/`userPromptSubmitted` → `resumed` (убирает красный после
  подтверждения), `agentStop` → `idle` и, в отличие от Codex, настоящий
  `sessionEnd` → `ended`. Это охватывает одноразовые `copilot -p` и завершение
  интерактивных сессий без чтения журналов. Названия сессий, создаваемые самим
  Copilot, находятся в его хранилище SQLite; отдельная зависимость ради них
  не нужна. Первый запрос из данных хука (`prompt`/`initialPrompt`) один раз
  задаёт имя сессии, без вызова LLM и чтения файлов. Принадлежность
  `broglow.json` определяется строкой команды `copilot-hook` внутри файла
  (в JSON нет комментариев); это защищает перезапись при установке и удаление.
- **Завершение** у opencode, где нет события выхода отдельной сессии,
  обрабатывается в три слоя: `process.on("exit")` плагина отправляет `ended`;
  проход `reconnected` служит страховкой; поскольку `run_event` при первом
  событии сохраняет `owner_pid` терминала, существующий
  `state::reap_ended_sessions` также убирает сессию opencode после завершения
  процесса. У `opencode serve` нет управляющего tty и `owner_pid`, поэтому
  остаются проход очистки и страховочный срок устаревания 24 часа.

<a name="conventions-gotchas"></a>

## Соглашения и особенности

- **Асимметрия автоматической настройки при первом запуске намеренная**
  (main.rs). Обе точки входа проверяют `hooks_registered()` — наличие команды
  хука broglow в `settings.json` — и действуют только при false. **TUI**
  (`first_run_setup_tui`) выполняет *полную* `install_hooks` с хуками и
  автозапуском, чтобы первый запуск завершал настройку после установки файла.
  **Служба трея** (`first_run_setup_daemon`) выполняет **только**
  `register_hooks`, без автозапуска: служба уже работает, а bootstrap/kickstart
  собственного LaunchAgent или отдельный `menubar` на Linux/Windows создали
  бы дубликат трея. Если `settings.json` не разбирается, он считается уже
  настроенным и не изменяется.
- **Не обрезайте пользовательские строки и ответы LLM по байтам.** Имена
  сессий берутся из запросов, сводок диалогов и заголовков LLM; это произвольный
  UTF-8. Обрезайте по символам (`truncate` / `char_prefix` в session.rs).
  Разрез внутри многобайтового символа вызывает panic и падение TUI при обновлении.
- **Запись `state.json` атомарна** — временный файл и переименование —
  и **защищена `.state.lock`**. Любое чтение с последующим изменением и записью,
  включая хуки и `x`/очистку в TUI, сначала получает `state::acquire_state_lock`,
  иначе можно затереть параллельное обновление.
- **Не записывайте состояние после ошибки чтения.** `hook.rs` возвращает
  `Unreadable`, если `state.json` не удаётся разобрать: например, из-за снимка
  во время записи или неизвестной будущей схемы. Вызывающий код не должен
  писать файл, иначе он сотрёт статусы остальных сессий.
- **Названия сессий принадлежат Claude.** На `SessionStart`/`UserPromptSubmit`/`Stop`
  хук читает последнюю запись `custom-title` (автоназвание приложения или `/rename`)
  из последнего 1 MiB транскрипта; она заменяет прежнее имя. Процесс
  именования запускается только при первом `Stop` сессии без названия. При запуске
  трей один раз вызывает `backfill_claude_titles`, чтобы простаивающие сессии получили
  название, не дожидаясь нового хода; существующее имя не перезаписывается.
- **Именование работает в отдельном процессе** и выставляет
  `BROGLOW_NAMING=1`, чтобы хуки вложенного вызова CLI `claude` ничего
  не делали и не создавали рекурсию. Он передаёт `--no-session-persistence`,
  чтобы вызовы именования не попадали в историю пользователя. Если CLI
  завершается с ошибкой (например, вход выполнен только в приложении), сессия
  получает название по первому запросу без блоков `<system-reminder>`.
  Существующее имя никогда не перезаписывается.
- **LED включаются явно, но чистая первая установка включает USB, если плата
  уже подключена** (`maybe_autoenable_led` в main.rs, вызывается из
  `install_hooks`). Условие — отсутствие `config.json`; повторная установка
  или существующий пользователь не получают LED, включённые вопреки явному
  отказу. Служба передаёт статусы только при `led_enabled`: через управление
  в сведениях о лампе (`Lamp details`) или `l` в TUI. На macOS tray также
  определяет новые USB-платы при отключённой передаче статусов и включает успешно
  добавленные новые лампы по BLE. Отрисовка остаётся read-only. USB VID `0x303A` обозначает
  Espressif, а не точную модель платы: перед прошивкой или командами порта
  определите реальное устройство. Сохраняйте USB по умолчанию и поведение
  явно указанного порта.
- **Нижняя строка всплывающего окна показывает состояние подключения лампы**
  (`renderLamp` в assets/popover.html, данные `LampPayload` из popover.rs).
  Она открывает сведения о лампе, а не переключает её. Включение/отключение —
  отдельное действие в этом прокручиваемом представлении; «Назад»/Escape
  возвращает к сессиям. В TUI сведения открываются клавишей `d`, прокручиваются
  стрелками или `j`/`k`, закрываются Escape. Оба основных списка сессий
  показывают краткий статус; полное состояние рабочего процесса и диагностика
  устройств находятся в подробностях. Реклама BLE или наличие USB ещё не
  означают подключение. Наличие USB позволяет включить USB-управление и запускает
  настройку новой лампы на macOS. BLE-устройства сохраняются между перезапусками и включаются без
  USB. Исправное `1/2` нормально для ламп дома и в офисе: одна недавняя успешная
  запись делает общий статус подключённым, при этом показаны состояния и
  количество отдельных устройств. Срок актуальности свой у каждой лампы;
  обновление другой лампы не продлевает его.
- **Bluetooth macOS привязан к идентичности установленного приложения.**
  LaunchAgent запускает `BroGlow.app/Contents/MacOS/broglow menubar`,
  а Info.plist приложения задаёт `NSBluetoothAlwaysUsageDescription`. Явная
  `ble scan` повторно запускает исполняемый файл из приложения. Локальная
  установка использует подпись ad-hoc со стабильным назначенным идентификатором;
  `BROGLOW_SIGNING_IDENTITY` позволяет задать настоящую подпись. Разрешение
  для Terminal само по себе не означает разрешение службы, запущенной при входе.
- **Учёт использования и расходов включается строго явно** (`usage_enabled`
  в настройках всплывающего окна; по умолчанию выключен). Он охватывает обе
  группы агентов: диалоги Claude с блоками `usage` для каждого сообщения и
  журналы Codex с накопительными событиями `token_count`, преобразуемыми в
  приращения с обнаружением сброса. Пока учёт выключен,
  `usage::spawn_refresher` **ничего** не делает: не сканирует JSONL диалогов,
  не читает учётные данные Claude Code и не обращается к OAuth-методу получения
  использования. Показатель трея (`apply_readout`) и раздел использования
  всплывающего окна остаются пустыми независимо от кеша. Разрешение на эту
  работу даёт именно включение. Исключение — подкоманда переднего плана
  `broglow usage`: её запуск сам по себе означает согласие на этот вызов,
  как и `broglow led`.
- **Экранируйте данные перед передачей оболочке.** Уведомления macOS строят
  строку AppleScript: сначала экранируйте `\`, затем `"`.
- Код отдельных платформ ограничивается `#[cfg(...)]` на месте: автозапуск
  в main.rs, скрытие консоли и mutex единственного экземпляра в menubar.rs,
  флаги отдельного запуска в spawn.rs.

<a name="esp32-board-optional"></a>

## Плата ESP32 (необязательно)

Прошивка ESP32-C3 SuperMini находится в `firmware/esp32-c3-supermini/`
(Arduino / PlatformIO). Красный/жёлтый/зелёный LED используют GPIO0/1/3 на
стороне GND, каждый через собственный резистор: 330 Ω для красного и жёлтого,
220 Ω для зелёного; катоды подключены к общему GND. Не используйте GPIO2:
он задаёт режим загрузки. BLE передаёт ровно один байт `R`, `Y`, `G` или `N`
с подтверждением; хост отправляет его сразу, при изменении и каждые две секунды.
Плата сбрасывает статус сессий через десять секунд после последнего корректного
обновления. Устаревшая связь, которая ещё считается подключённой, оставляет
LED выключенными; после отключения плата возвращается к индикации настройки
или ожидания. Подключённый BLE-клиент владеет управлением LED; команды
последовательного порта работают при отключённом BLE. Прошивайте через
PlatformIO или описанную процедуру esptool для готовых файлов; обновление
прошивки через протокол приложения не поддерживается.

Запись BLE требует шифрования и сопряжения LE Secure Connections Just Works.
После обычной загрузки удержание BOOT/GPIO9 три секунды открывает окно
сопряжения на 60 секунд; десять секунд запрашивают удаление всех сохранённых
сопряжений платы. Отсутствие сопряжений при старте также открывает окно.
Just Works не обеспечивает аутентификацию против MITM. Индикация использует
восьмибитный PWM с частотой 2 кГц: при сопряжении красный/жёлтый/зелёный
загораются по очереди; без сопряжения мигают все три; при ожидании с сохранённым
сопряжением каждые 30 секунд идёт тусклый импульс. Первая корректная
зашифрованная запись в каждом подключении вызывает одну подтверждающую
вспышку 250 мс, затем действует свежий статус, включая `N`; отключение,
потеря аутентификации или устаревание отменяют вспышку.

GPIO8 по умолчанию управляет одноцветным LED с активным низким уровнем:
один/два/три импульса соответствуют зелёному/жёлтому/красному. Флаги сборки
задают вывод, полярность и яркость либо отключают его через
`BUILTIN_LED_PIN=-1`. Пользователь подтвердил быстрое синее мигание при
сопряжении; остальные видимые режимы не проверены. Диагностика `?` через
последовательный порт сообщает сохранённый статус, заданные включение/выключение
и заполнение PWM, режим, вывод, сопряжение и сохранённые связи. Это не чтение
состояния выводов и не доказательство видимого света. `N` не различает
отключение лампы в приложении и отсутствие Mac, поэтому импульсы ожидания
после разрыва связи могут возобновиться; `WAIT_LED_BRIGHTNESS=0` убирает их.
Подробные тайминги индикации и настройка находятся в руководстве по оборудованию.

Команды прошивки и подтверждённое состояние оборудования также смотрите
в руководстве по оборудованию.

<a name="ci"></a>

## CI

`.github/workflows/ci.yaml` запускается для PR и отправок в master:
`cargo fmt --check`, затем clippy (`-D warnings`) и `cargo test` на
ubuntu/macos/windows. Тесты в tests/ проверяют *собранный исполняемый файл*
сквозным образом: события хуков Claude в stdin → проверки `state.json`;
автоматическое именование с подставной `claude` в PATH (hook_lifecycle.rs,
только Unix — на Windows нельзя перенаправить `$HOME`); нормализованные
события агентов → `state.json` (event_lifecycle.rs, только Unix по той же
причине); отдельные события Copilot через адаптер (copilot_lifecycle.rs,
только Unix по той же причине); цикл установки/удаления с плагином opencode
и файлом хуков Copilot (install.rs, только Linux — на macOS он выполнил бы
`launchctl bootout` для настоящей службы на компьютере разработчика);
базовые проверки CLI, включая разбор встроенного плагина opencode через
`node --check`, если node доступен (cli.rs, все платформы). Для нового
поведения предпочитайте расширение этих проверок модульным тестам.
Событие `Stop` с `transcript_path` запускает настоящий отдельный процесс
именования: в тестах нужно опустить это поле или заранее задать имя.

В `tests/js/` находятся **интеграционные** тесты плагина opencode
(`node --test`, CI на Linux). Они передают настоящему
`assets/opencode-plugin.js` реальные структуры событий opencode и проверяют
`state.json`, записанный собранным исполняемым файлом. Именно эту границу
не проверяют тесты Rust, которые напрямую вызывают `broglow event`.
`exit-child.mjs` — вспомогательный процесс, а не тест: он позволяет реально
проверить завершение через `process.on("exit")` плагина.

`.github/workflows/release.yaml` собирает и упаковывает релизные исполняемые
файлы для каждой платформы. CI также собирает закреплённое окружение C3
PlatformIO и запускает проверки с имитацией аппаратуры на хосте. Набор
JavaScript включает регрессионную проверку статуса лампы во всплывающем окне,
обновляемого рабочим процессом.
